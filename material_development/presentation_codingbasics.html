Section 1.1: Components of Code

Basic Call:

  • [ASSIGNMENT] <- FUNCTION(PARAMETER = X)
  • data <- read.csv(data = "data/data_wales_education.csv")

Terminology:

  • <- assignment arrow, or to assign
  • ? prefix a function to open the help page
  • Variables are stored pieces of data in your global environment stored through assignment arrows
  • Arguments are those specified in functions and as specified through the =
  • Functions are complex pre-compiled scripts to save you time!

  • Select a line of code and hit ctrl + enter

Section 1.3: Basic Errors

Rstudio Cues:

RStudio will highlight errors by: - Red Cross in a Circle (hovering over will expand the issue) - Red Line under the specific issue in question (like spellchecker in word) - Orange Line under specific issues which may be a problem

Section 1.3: Errors in the Console

  • When an error occurs, they will typically be structured
    • Error in [X] : [REASON]
  • For example, for the call:
    • summary()
    • Here we have left out any argument in the summary function
    • Error in summary.default() : argument "object" is missing, with no default
  • There may also be additional warning messages:
    • In addition: Warning message: [DETAIL]

Section 1.3: Common Error Types

  • Syntax Errors
    • Unexpected amount of punctuation (too many)
    • Unexpected amount of punctuation (to few)**
    • Incomplete or missing argument
  • Incomplete connections
    • File, source or content is not in the right place!

NOTE: when there is not enough punctuation, this can result in no error triggers, rather just a hanging > and will proceed no further.

Section 1.3: Less Common Error Types

  • These commonly occur during the implementation of code, after a system is deployed.

  • Logical, Arithmetic or Runtime Errors

    • These result from errors internally, such as:
    • Dividing by zero
    • Missing Internal Packages
    • Incorrect usage by users

  • Linker or Resource Errors

    • These result from internal system errors, such as inadequate system resources, or failures in the internal links

Section 1.3: Overcoming Errors

  • Read the error message presented (usually it highlights the problem!)
  • Utilise the debugger in RStudio
  • Isolate the problem, understanding what contributes to that function/line
  • Ask for help!

Section 2: Understanding Datasets

Section 2.1: Loading in different data

Data can be loaded into R through:

  • Manual Loading:
    • Directly from the Working directory
    • Directly through the import dataset tab
  • Script Loading:

Section 2.1: Manual Loading

Loading data from Working Directory

  • The location where R will look to find and save files managed in RStudio
  • Use getwd() to pull your current working directory.
  • Use setwd() to set your working directory
  • You can also access, change and view your working directory via the GUI
    • Files Panel (Bottom Right) >> More >>
    • Set as Working Directory
    • Go to Working Directory

Section 2.1: Manual Loading

  • Data can be loaded into your RStudio Environment in multiple ways
  • The easiest method is finding the data file (.csv, .json, .tsv etc) in your files panel
  • When selected it you can select to import dataset which handles a majority of the process

Section 2.1: Script Loading

  • You can also use script or code to load in your data.
    • load() - .RData files
    • readRDS() - .RDS files
    • read_csv() - .csv files - readr
    • read_tsv() - .tsv files - readr
    • read_delim() - delim files (.txt, any other variant) - readr
    • read_spss()/read_sav() - SPSS files (.spss/.sav) - haven
    • read_sas()/read_xpt() - SAS files (.sas7bdat) - haven
    • read_dta() - Stata files (.dta) - haven
    • read_excel()/read_xls()/read_xlsx() - Xlsx files - readxl
  • This list isn’t exhaustive!! If in doubt, Google it!!

Section 2.2: Understanding types of Data

Data comes in multiple different types of structure:

  • Vector: String of multiple elements
  • Matrix: Multiple vectors formed into columns and rows (which share the same data type)
  • Arrays: Similar to matrices but more than 2 dimensions
  • Data Frames: Multiple vectors formed into columns and rows, each columns indicates a different variables
  • Tibbles: Simple Dataframes
  • Lists: An ordered collection of objects, merged of one or multiple types

Section 2.2: Understanding types of Data

Data also have multiple different types which we can see through class():

  • Logical, for example: TRUE or FALSE
  • Numerical, for example: 10.7, 1031, 5
  • Integer, for example: 1L, 55L, 701L (L declares integar)
  • Character, for example: “k”

This also includes:

  • Dates, for example: “2011-01-02”, “Friday”, “03-01-29 09:30:40”

  • Factors - these can be anything and are defined in Levels

  • Dates are an oddly complex form of variable. Which we won’t cover during this course.

Section 2.3: Viewing Data

Although you can use the GUI to easily view data structures, you can preview data using:

  • View() - Opens a new pane panel to display the data
  • head() - Prints the first 5 rows of the dataset into the console
  • tail() - Prints the last 5 rows of the dataset into the console

Additionally, you can examine the structure of the dataset:

  • str() - highlights the overall structure of the dataset
  • ncol() - prints the number of columns in the dataset
  • nrow() - prints the number of rows in the dataset

You can also examine an overall summary of the dataset:

  • summary() - prints a summary of the dataset given

Section 2.1: Clean and Readable Code

When writing code, there are many style guides available in general these will help you to appropriately:

  • Comment or Document your code
  • Name your Functions, Variables or Classes
  • Separate elements of your code with white space
  • Use indentation to make sure your code is readable
  • Provide other useful guidance for formatting

In general, these are guides and not conventions which can be applied to the letter, as these are typically closer to an art form, than a science.

Section 2.1: Shared Conventions

When writing code, having agreed upon conventions is vital, this includes:

  • Naming Conventions:
    • How are you naming your variables? Var1 or var1 or var_1?
  • Syntax Convention:
    • What spacing will you use?
    • What Line Length will you use?
    • What indentation will you use?
  • How will you make sure others can understand your code?

Section 2.1: Informative Names

Where possible, use unique, informative names for elements within your project, these should:

  • Provide clear and concise names for variables, functions and classes
  • Make it understandable to the reader its purpose
  • Be a balance between being an explicit description and easy to reference in your code

Section 2.1: Clear Commenting

Commenting your code, allows you to provide reasoning, explanations and details to your code.

  • A comment should begin with a # and most often occurs before a code chunk
  • Use Comments sparingly and with purpose!

Please note:

  • Over commenting can become confusing, take up time and make it difficult to read
  • Under commenting can make your code hard to follow, and assumptions to be made
  • It takes practice to find the right balance when commenting

Section 2.1: Main Takeaways

  • When starting a project, choose a style convention and stick to it
  • Each team, organisation and person will have a style guide preference, use the most appropriate for your work
